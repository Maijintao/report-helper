# 问答备稿

问答和正文分开写，放在稿子末尾。现场最慌的是问答，这部分要写得比正文更硬。

## 问题从哪来

按下面五类各准备两到三个，按被问到的可能性排序，最可能被问的放最前。

1. **增量**：你们相对基线、往届或竞品，多做了什么
2. **替代方案**：为什么不用另一种做法
3. **概念质疑**：你说的 X 到底算不算 X
4. **风险与边界**：出错怎么办，什么情况下失效
5. **完成度**：现在真能演示到什么程度，哪些还没验证

问题用老师或评审会说的原话写，不要概括成「关于系统架构的提问」。

## 回答口径怎么写

每题三段，控制在 120 字以内：

1. 一句结论，直接回答被问的那件事
2. 一句依据，来自本项目的证据，优先数字、日志、测试记录
3. 一句边界或适用条件

格式照抄，问题和答案都用正文语气，不写小标题式的概括：

```markdown
### 你们怎么证明 rubrics 是公平的？

回答口径：

> rubrics 不是只看最终结论，而是拆成事实证据、根因链路、影响范围、恢复建议、反证排除和负分项。
> 每个得分点都要求能从 case 允许的工具边界里查到证据。
> 也就是说，评分依据不是「像不像标准答案」，而是是否拿到了可验证证据。
```

答案写成能直接念的完整句子，不要写成要点。三条依据要能对应正文里的某一段。

## 答不上来怎么办

准备两句兜底话，不要现场编数字：

- 「这块我们没做验证，目前只能说到 X，再往下需要补一组实验。」
- 「这个方案我们评估过，代价是 Y，所以这次没选；如果要做，我会先验证 Z。」

承认没做，比编一个数字安全。

## 交付形式

问答放在正文后面，用二级标题分开，中间空一行。需要单独给老师看时，可以导出成另一个文件。
