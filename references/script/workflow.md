# 稿件流程

## 整理本次资料

确认汇报场景、主要听众、发言时长、发言人负责的部分、已有幻灯片和演示条件。用户已给出的信息直接使用。影响事实或汇报目的的缺口集中询问，其他缺口用明确的待确认标记。

每项关键成果、数字和演示结果都要能追溯到当前项目资料。区分已实现、已验证、计划中和材料未确认。成果有统计口径或适用条件时，将必要条件放在对应的句子附近。资料相互冲突时标记待确认，保留各自对应的口径。

## 选择讲述顺序

按本次汇报最需要回答的问题安排内容。需要介绍技术成果时，优先选一个真实的用户场景、案例或演示作为主线。沿着同一个例子依次讲清楚遇到的问题、关键做法、可以观察到的结果。多个技术点共用一个例子时，每一段回答一个新问题。

已有页面时，按页号和标题安排讲稿。保留页面之间的过渡，例如先指给听众看结果，再解释产生这个结果的关键步骤。

## 写成可以直接讲的稿件

- 首次出现项目专用名词时，简短说明它在这个场景里的作用。技术标识符保留原名。
- 用完整的口头句子。讲机制时交代触发条件、关键动作和结果。根据实际贡献选择「我负责」或「我们实现」。
- 用 `[翻页]`、`[演示]`、`[交给下一位]` 标记必要动作。演示写清操作、预期出现的内容和要指给听众看的位置。
- 把较长的实现说明、特殊场景和技术取舍放入问答备稿。每个回答先给结论，再给当前项目的依据和适用条件。根据本次正文的关键说法准备追问。

## 核对并排练

逐段核对数字、完成状态、个人与团队贡献、页面顺序和演示入口。将演示等待、翻页和交接计入时长。根据真实朗读结果调整稿件。只能估算时，标明是预计用时。

交付可单独朗读的正文。需要答辩或预演时，把问答与正文分开。保留需要发言人确认的事项，便于排练时逐项核对。
